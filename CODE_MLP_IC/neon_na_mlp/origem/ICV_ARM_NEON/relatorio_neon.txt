O professor forneceu uma implementação de referência em C calculando o produto

-------------------------------------------------------------------------------
2. CONCEITOS FUNDAMENTAIS
-------------------------------------------------------------------------------

2.1 Produto Interno (Dot Product)
----------------------------------
Dados dois vetores a e b de tamanho N, o produto interno é:

    resultado = a[0]*b[0] + a[1]*b[1] + ... + a[N-1]*b[N-1]


2.2 Implementação escalar
--------------------------
O código de referência implementa o dot product com um loop simples:

    int32_t dot_product_int8(const int8_t *a, const int8_t *b, int len) {
        int32_t ret = 0;
        for (int i = 0; i < len; i++)
            ret += a[i] * b[i];
        return ret;
    }

A CPU executa isso um elemento por vez. Para LEN = 16*1024 = 16384 elementos,
são 16384 multiplicações seriais.

2.3 SIMD e NEON
----------------
A Pi 4 tem um processador ARMv8 com unidade SIMD chamada NEON.
SIMD = Single Instruction, Multiple Data: uma instrução opera em vários dados
simultaneamente.

Os registradores NEON têm 128 bits. Para float32 (32 bits), cabem 4 floats
por registrador. Para int8 (8 bits), cabem 16 elementos.

Exemplo visual para float32:

    reg v0: [ a0 | a1 | a2 | a3 ]   ← 4 floats
    reg v1: [ b0 | b1 | b2 | b3 ]   ← 4 floats
            ↓ instrução fmla
    reg v2: [ a0*b0 | a1*b1 | a2*b2 | a3*b3 ]

Uma instrução fez o trabalho de 4. Para 16384 elementos, são apenas 4096
iterações — ganho teórico de 4x. Para int8, o ganho teórico é 16x.

2.4 Intrinsics
---------------
As instruções NEON existem em nível de assembly:

    fmla v2.4s, v0.4s, v1.4s   ; v2 += v0 * v1 (4 floats simultâneos)

Escrever assembly puro é trabalhoso. Intrinsics são funções C que mapeiam
diretamente para essas instruções — você escreve C normal, o compilador
emite a instrução exata sem overhead intermediário:

    // C com intrinsic:
    acc = vmlaq_f32(acc, va, vb);

    // assembly gerado:
    fmla v2.4s, v0.4s, v1.4s

O header <arm_neon.h> define todas essas funções e os tipos vetoriais
(float32x4_t, int8x16_t, int32x4_t, etc.).


-------------------------------------------------------------------------------
3. IMPLEMENTAÇÃO — dot_neon.c
-------------------------------------------------------------------------------

Arquivo com 6 funções: 3 escalares (referência do professor)
+ 3 versões NEON.

Decisões técnicas por tipo:

    int8:    16 elementos/iteração
             vmull_s8 eleva int8→int16 (necessário: int8*int8 pode estourar int8)
             vpadalq_s16 acumula em int32 (widening pair-wise add)

    int32:   4 elementos/iteração
             vmlaq_s32 multiply-accumulate direto (sem risco de overflow no acc)

    float32: 4 elementos/iteração
             vmlaq_f32 multiply-accumulate direto

Redução horizontal (vetor → escalar) ao final de cada função:
    vadd + vpadd + vget_lane

Nota sobre float32: o resultado NEON pode divergir levemente do escalar.
Ponto flutuante não é associativo — a ordem de acumulação vetorial difere
da escalar, gerando erros de arredondamento distintos. Isso é comportamento
esperado, não um bug.

Compilação:
    aarch64-linux-gnu-gcc -O2 -static -o dot_neon dot_neon.c

Envio para a placa:

5. EXPERIMENTO — AUTO-VETORIZAÇÃO DO GCC
-------------------------------------------------------------------------------

5.1 Pergunta central
---------------------
O compilador GCC já vetoriza automaticamente o código escalar do professor?
Se sim, o resultado é equivalente ao NEON manual?

5.2 Metodologia
----------------
Compilar dot_scalar.c (código do professor intocado) com a flag
-fopt-info-vec-optimized, que faz o GCC reportar quais loops vetorizou.

    aarch64-linux-gnu-gcc -O2 -fopt-info-vec-optimized -static \
        -o dot_scalar_O2 dot_scalar.c 2> vec_O2.log

    aarch64-linux-gnu-gcc -O3 -fopt-info-vec-optimized -static \
        -o dot_scalar_O3 dot_scalar.c 2> vec_O3.log

5.3 Resultado dos logs
-----------------------

vec_O2.log:

    dot_scalar.c:27:23: optimized: loop vectorized using 16 byte vectors
    dot_scalar.c:18:23: optimized: loop vectorized using 16 byte vectors
    dot_scalar.c:9:23:  optimized: loop vectorized using 16 byte vectors

vec_O3.log:
    dot_scalar.c:9:23:  optimized: loop vectorized using 16 byte vectors
    dot_scalar.c:9:23:  optimized: loop vectorized using 8 byte vectors
    dot_scalar.c:18:23: optimized: loop vectorized using 16 byte vectors
    dot_scalar.c:27:23: optimized: loop vectorized using 16 byte vectors
    dot_scalar.c:27:23: optimized: loop vectorized using 16 byte vectors
    dot_scalar.c:18:23: optimized: loop vectorized using 16 byte vectors
    dot_scalar.c:9:23:  optimized: loop vectorized using 16 byte vectors

Mapeamento linha → função:
    linha 9  → dot_product_int8
    linha 18 → dot_product_float32
    linha 27 → dot_product_int32

O GCC vetorizou os 3 loops em ambos os níveis, usando vetores de 128 bits.

Detalhe -O3: linha 9 (int8) aparece também com 8 bytes — o compilador gerou
um epilogo para processar elementos residuais caso o tamanho não seja múltiplo
exato do vetor. O -O2 não fez isso.

5.4 Comparação de assembly
---------------------------
Geração dos arquivos .s:

    aarch64-linux-gnu-gcc -O2 -S -o dot_scalar_O2.s dot_scalar.c
    aarch64-linux-gnu-gcc -O2 -S -o dot_neon_O2.s   dot_neon.c

Filtragem de instruções NEON relevantes:

    grep -E 'fmla|fmul|mla|smlal|ld1|st1|\.4s|\.8h|\.16b' dot_scalar_O2.s
    grep -E 'fmla|fmul|mla|smlal|ld1|st1|\.4s|\.8h|\.16b' dot_neon_O2.s

--- dot_scalar_O2.s (int8, auto-vetorizado) ---
    movi    v31.4s, 0
    smull   v28.8h, v30.8b, v29.8b     ; int8x8 * int8x8 → int16x8 (metade baixa)
    smull2  v30.8h, v30.16b, v29.16b   ; int8x8 * int8x8 → int16x8 (metade alta)
    saddw   v31.4s, v31.4s, v28.4h     ; widening add parcial 1
    saddw2  v31.4s, v31.4s, v28.8h     ; widening add parcial 2
    saddw   v31.4s, v31.4s, v30.4h     ; widening add parcial 3
    saddw2  v31.4s, v31.4s, v30.8h     ; widening add parcial 4
    addv    s31, v31.4s                 ; redução horizontal
    → 6 instruções para acumular 16 elementos

--- dot_neon_O2.s (int8, NEON manual via vpadalq_s16) ---
    smull   v28.8h, v1.8b,  v28.8b     ; int8x8 * int8x8 → int16x8 (metade baixa)
    smull   v0.8h,  v27.8b, v0.8b      ; int8x8 * int8x8 → int16x8 (metade alta)
    sadalp  v30.4s, v28.8h             ; pairwise add + acumula em int32
    sadalp  v30.4s, v0.8h              ; pairwise add + acumula em int32
    → 4 instruções para acumular 16 elementos

Para int32 e float32 os assemblies são equivalentes entre as duas versões.


-------------------------------------------------------------------------------
6. CONCLUSÃO
-------------------------------------------------------------------------------

    Tipo     | Auto-vetorização GCC -O2 | NEON manual | Diferença
    ---------|--------------------------|-------------|--------------------
    int8     | 6 instruções/iter        | 4 instr/iter| manual mais eficiente
    int32    | equivalente              | equivalente | nenhuma
    float32  | equivalente              | equivalente | nenhuma

O compilador já vetoriza os 3 loops automaticamente com -O2.
Para int32 e float32, o código gerado automaticamente é equivalente ao manual.

Para int8, o NEON manual é mais eficiente: a instrução sadalp (signed add
long pairwise) faz em uma operação o que o compilador faz em duas (saddw +
saddw2), resultando em 4 instruções por iteração contra 6 do auto-vetorizador.

Isso responde a pergunta central: escrever intrinsics na mão é útil quando
o compilador não consegue identificar a instrução mais densa disponível.
Para tipos de dados menos convencionais como int8 com acumulação widening,
o conhecimento da ISA permite superar o auto-vetorizador.
